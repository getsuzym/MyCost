# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

MyCost is a SwiftUI + SwiftData iOS app (iOS 17, Swift 5.0, bundle id `com.getsuzym.MyCost`) for tracking personal spending. Its distinguishing feature is importing transactions from banking screenshots via on-device OCR, then reviewing/deduping them before they are saved.

## Build & test

`xcodebuild` requires a full Xcode; this machine may have only Command Line Tools selected:

```sh
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
xcodebuild -project MyCost.xcodeproj -scheme MyCost \
  -destination 'platform=iOS Simulator,name=iPhone 16' build
```

### Running tests

`MyCostTests` (XCTest unit tests, `@testable import MyCost`) is wired into `project.pbxproj` as a unit-test bundle with `TEST_HOST` = the `MyCost` app. Run it:

```sh
xcodebuild test -project MyCost.xcodeproj -scheme MyCost \
  -destination 'platform=iOS Simulator,name=iPhone 17' -only-testing:MyCostTests
# single test:
xcodebuild test ... -only-testing:MyCostTests/MyCostTests/testRecurringSuggestionDetectsAnnualPayments
```

If `xcode-select` points at the Command Line Tools, prefix commands with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` instead of running `sudo xcode-select`.

The full unit + UI suites are green. (A `MyCostTests` full run can still show one flake — `testMultipleMonthsStaySeparated` — from latent test-ordering shared state that predates the target being wired up; it passes in isolation and is unrelated to feature work.)

`MyCostUITests` is a UI-test-bundle target (`-only-testing:MyCostUITests`). Tests launch with `-ui-testing`, which makes `MyCostApp` use an in-memory `ModelContainer` (default categories seeded on launch). Views expose `accessibilityIdentifier`s in `screen.element` form (`review.saveApproved`, `transactionEditor.merchant`, `dashboard.openMonth`, `dashboard.importScreenshots`, …). **Three bottom tabs**: Dashboard, Recurring, More (`MoreView` → Settings [`SettingsView` — Budget / Recurring Reminders / Backup / Privacy, every preference in one place] / Organize [Categories / Rules] / Manage [All Transactions / Tags / Accounts / Recently Deleted]). Categories and Rules are configuration screens visited occasionally, not daily-use, so they don't get their own tab. There is no Transactions tab either — the Dashboard's Recurring / Non-Recurring drill-downs and Month Detail cover it; the full `TransactionHistoryView` (with search) lives under More → All Transactions. Import and Review are **not** tabs — see "Navigation & the persistent review session" below. The add-transaction UI tests exist as a crash guard for the SwiftUI diff issue below. Icon-only controls (the month steppers on Dashboard / Recurring / History / Month list / Category detail) carry `.accessibilityLabel` ("Previous month" / "Next month") in addition to their test identifier; Dashboard and the Recurring tab are `.refreshable` (data is `@Query`-live — the gesture is a re-render + spinner).

### Add/save must not restructure a `List` and animate the app at once

`ContiguousArrayBuffer.swift:692` / `AppGraph.shared may only be set once!` on "adding a transaction" came from a `List` doing several structural changes in one `@Query`-driven update (a `Section` appearing, an `if/else` flipping `ContentUnavailableView` ↔ `ForEach`) **while** `.toastHost()` animated the whole `TabView` (a toast now fires on every save). Rules that keep it stable, applied to `DashboardView`, `MonthDetailView`, `ReviewTransactionsView`: never wrap the whole app in `.animation(_:value:)` — `ToastHost` animates only its overlay `ZStack`; don't gate a `Section` or swap `ForEach`↔`ContentUnavailableView` on data that changes on add — keep the `Section`/`ForEach` always present and show an empty-state `Text` as a sibling row; compute a recomputed summary/list **once** per `body` (`let x = x; return List{…}`) so its `ForEach` diffs against one snapshot; and every `Identifiable` used in a `ForEach` over a *recomputed* collection needs a value-derived `id` (see `CategorySpend.id`, `RecurringPaymentSuggestion.id`), never `let id = UUID()`.

### project.pbxproj is hand-maintained

The project file uses synthetic sequential IDs (`0000...`) and is **not** a file-system-synchronized group. Adding a Swift file requires four manual edits: a `PBXBuildFile` entry, a `PBXFileReference` entry, a child entry in the correct `PBXGroup`, and an entry in the `Sources` build phase. (See how `OCRTransactionImportCoordinator.swift` was added.) Test-target files go in the `MyCostTests` group and the `0000…09A6` Sources phase.

## Architecture

**No view models for CRUD.** SwiftUI views bind directly to SwiftData `@Model` instances for editing. Reusable logic lives in `Services/` as stateless `struct`/`enum` types that operate on plain arrays and value-type snapshots, so they are unit-testable without a `ModelContainer`.

**Schema is declared twice** — in `MyCostApp.swift` and in the test `setUpWithError`. Both lists (`Transaction`, `Category`, `MerchantRule`, `RecurringPayment`, `Account`, `Budget`, `Tag`, `TransactionSplit`, `DeletedTransactionRecord`) must stay in sync when a model is added. All model relationships use `.nullify`. New `Transaction` fields for amount normalization (`normalizedAmount`, `transactionDirectionRawValue`, `accountTypeRawValue`, `countsAsSpending`, `needsDirectionReview`) are all `= <default>` so they're a lightweight migration on existing stores.

**No AI.** There is no network/LLM categorization. The AI provider connection, Keychain secret store, OpenAI/Anthropic providers, and their settings screen were removed. `MerchantCategorizationCoordinator` is a small synchronous type with three outcomes: `.ruleMatch` (user `MerchantRule`) → `.localMatch` (`LocalMerchantCategorizer` known-merchant table) → `.unresolved` (manual / Uncategorized). Merchant learning stays: renaming/recategorizing a transaction can be saved as a `MerchantRule` (`MerchantRuleService.learnRule`).

### Screenshot OCR import pipeline (the core cross-file flow)

1. `ImportView` → `ImagePicker` (multi-select `PHPicker`, `selectionLimit = 0`, returns `[PickedImage]`) → `ScreenshotBatchImportService.process(_:progress:)`, which runs `ScreenshotImportService.processScreenshot(_:referenceDateOverride:)` **once per screenshot** (see "Batch multi-screenshot import" below).
2. `VisionOCRService` (conforms to `OCRServicing`, injectable for tests) returns `[RecognizedTextBlock]` (text + normalized `boundingBox` + confidence), sorted top-to-bottom, left-to-right.
3. **Spatial grouping (primary).** Blocks become `[OCRTextObservation]` (Vision's bottom-left boxes flipped to a top-left, y-down space). `TransactionRegionDetector.detectRegions(from:dividers:)` clusters observations into rows and cuts them into `TransactionRegion`s — on supplied divider lines (nearest row gap), on abnormally large vertical gaps, at date-only section headers, and before every amount-bearing row after the first. `TransactionGrouper.candidates(from:originalOCRText:)` then assigns fields **by position, not OCR order**: amount from right-aligned currency text (conflicting right-aligned amounts → `amount = nil` + `.multipleAmounts`/`.ambiguousLayout`), merchant from left-side rows (multi-line preserved), date/status from region text with a carried section-header date. Account chrome above the first date header and rows with no amount and no own date are dropped. Each candidate keeps its `observations` (text/frame/confidence) for review and the `#if DEBUG` `OCRDebugOverlayView`.
   - **A recognized date is never the merchant.** `TransactionTextHeuristics.detectDate` recognizes `2026-09-02`, `09/02`, `Sep 2`, and the relative words `Today` / `Yesterday` / `Tomorrow` (resolved against `referenceDate`, no year inference). Both the grouper and the flat parser strip the matched date and then run `heuristics.isEssentiallyJustADate(merchant)` — if what's left is still just a date, the merchant is cleared and `.missingMerchantDescription` / `.possibleNonTransactionLine` set, for the user to fill in.
   - **`BankLayoutProfile`** is an *optional* per-bank tuning of the generic parser, not a replacement. `BankLayoutProfile.identify(in: ocrText)` matches lowercased signature phrases and returns a profile carrying a `TransactionGrouper.Configuration`; an unrecognized layout returns `.generic` (`.default` config). `ScreenshotImportService` picks the profile and passes its config to the grouper; the chosen profile name is on `ScreenshotImportResult.layoutProfileName`.
   - **Section-date headers.** `TransactionTextHeuristics.dateOnlyHeader` recognizes a row that is essentially just a date, **tolerating a leading weekday name** ("Sunday August 2, 2026" — TD's layout). `TransactionRegionDetector` isolates that row so the grouper emits `.sectionHeader(date)`, and `TransactionGrouper.candidates` carries the date forward to **every** dateless row beneath it — plus a candidate that carried its own explicit date (a header glued onto the day's first transaction) also updates the carried section date. A dateless row never falls back to `now`. `cleanMerchantDescription` also strips a leading weekday that precedes a month+day, so "Sunday …" never sticks to a merchant name.
   - `TransactionCandidateParser.parse(lines:)` is the **flat-text fallback**, used only when spatial grouping returns nothing (`ScreenshotImportResult.usedSpatialGrouping == false`). It and the grouper share field parsing via `TransactionTextHeuristics` (amount/date/status regexes, merchant cleanup, `dateOnlyHeader`). Refunds parse as negative amounts.
   - One `referenceDate` (captured per `processScreenshot` call, returned on `ScreenshotImportResult`) is threaded to the grouper, the flat parser, and `replaceCandidates`, so a year-less date ("Aug 28") is inferred consistently. `dateByInferringYear` uses the current year, stepping back a year only if that would be >31 days in the future.
4. `OCRTransactionReviewStore` is a `@StateObject` on `RootTabView` shared via `.environmentObject`; it **is** the persistent review session. `replaceCandidates(_:merchantRules:referenceDate:)` maps candidates to `[OCRTransactionDraft]`. `hasActiveSession == !drafts.isEmpty`. `OCRTransactionDraft.isUncertain(_:)` drives "Needs review" highlighting; `canImport` gates saving.
5. `ReviewTransactionsView` prioritizes the fields that need attention: include/exclude, merchant, amount, **category** (picker sorted with `alphabetizedByName()`), **recurring** (a per-row `isRecurring` toggle + an optional "mark future transactions from this merchant as recurring"), and a **rule-status row** — `draft.categorizationStatus` (`.ruleMatched` / `.categorized` / `.uncategorized`, the last orange) next to an **"Edit Rule"** button. Edit Rule opens `MerchantRuleEditorView` in a sheet on the draft's best-matching rule (or a new one pre-filled from the draft, with the draft's OCR text seeded into the live "This rule matches: …" preview); on save, `ocrReviewStore.applyRule(_:toDraft:)` re-applies it immediately and, if other drafts also match (`draftsMatching`), a confirmation offers `applyRuleToBatch`. Deleting the rule calls `clearAppliedRule`. Pending/Posted is **not** in the Review UI — `OCRReviewField` has no `.status` case — but `OCRTransactionDraft.status` is still kept and stored on the `Transaction` for duplicate detection. The category Picker uses a custom `Binding` whose `set` calls `markCategoryUserSet` so a rule-matched row the user overrides flips to `.categorized` (programmatic rule/suggestion assignment doesn't). It also has an **Account Type** section, a deterministic **"Suggest category"** button, Select All / Deselect All, and "View source" (batch). `saveApprovedTransactions` `AccountService.upsert`s the types then runs `flagDuplicateDrafts`.
6. **`OCRTransactionImportService.importDrafts(_:categories:accountTypesByName:existingTransactions:existingRules:modelContext:)`** (extracted from the view so the whole path is testable) inserts a `Transaction` per importable draft, copying `draft.isRecurring` onto it and running `TransactionNormalizer` with the draft's account type (see below) so `normalizedAmount` / `countsAsSpending` / `transactionDirection` are stamped and ambiguous rows counted in `OCRDraftImportOutcome.reviewFlaggedCount`. A `markFutureRecurring` draft also `learnRule`s a `.contains` rule keyed on the merchant name with `isRecurring = true`. It calls `save()` once, then does a post-save `fetchCount` and returns an `OCRDraftImportOutcome` (`persistedTransactionCount`, `saveError`, inserted/merged IDs). `os.Logger(subsystem: "com.getsuzym.MyCost", category: "OCRImport")` logs the count, each inserted entity, and the save result. `saveError` surfaces in a `.alert` (drafts + thumbnails kept for retry); otherwise drafts are cleared and the footer shows the persisted count.

There is one source of truth — the app's `ModelContainer.mainContext`. Every screen reads it via `@Query`; nothing copies `Transaction` arrays between screens (`SpendingAnalytics` and `MonthlyTransactionsService` are pure functions fed by a `@Query`).

### Batch multi-screenshot import — `ScreenshotBatchImportService`

`ImportView` is presented as a **sheet** (`nav.route == .importPicker`) from the Dashboard's `photo.badge.plus` toolbar button, not a tab. It auto-opens the multi-select picker on appear, then a 4-phase wizard (`Phase`: idle → preview → processing → done). On processing completion: **> 0 detected → `nav.finishImportProcessing(detectedCount:)` switches the sheet to `.review`** (auto-navigation, even if some screenshots failed — Review shows the warning banner), unless the account type still needs confirming, in which case it stops at `Phase.accountType` first (see "Account type awareness" below); 0 detected → stays on the `.done` phase for a retry. `ScreenshotBatchImportService.process([BatchScreenshotInput], progress:)` loops the **existing single-screenshot pipeline** per image — raw OCR text is never concatenated across screenshots before grouping; each screenshot produces its own candidates, then they're appended in screenshot order. It is fault tolerant: a `processScreenshot` throw becomes a `BatchScreenshotFailure(label:reason:)` and the loop continues. It stamps every candidate's `sourceScreenshotID`, shares **one `referenceDate`** across the batch (`referenceDateOverride`), and retains only a downscaled `thumbnail` per screenshot (full-resolution `UIImage`s live in `ImportView.queued` and are dropped the moment processing ends). Injection: `ScreenshotBatchImportService(importService: SingleScreenshotProcessing = ScreenshotImportService())` — tests pass a `StubSingleScreenshotProcessor` (canned `Result` per call) so batch logic is exercised without OCR.

`OCRTransactionReviewStore.replaceBatch(candidates:thumbnails:info:merchantRules:referenceDate:)` installs the combined session: `sourceThumbnails: [UUID: UIImage]` (for "View source" in a Review row), `batchInfo` (`OCRBatchSessionInfo` — succeeded screenshot count + failed labels, drives the Review banner), plus `selectAll()` / `deselectAll()` for the Review toolbar. Dedup is unchanged — the one `flagDuplicateDrafts` pass in `saveApprovedTransactions` already compares each draft against existing transactions **and earlier drafts in the batch**, so the same transaction appearing in two overlapping screenshots is flagged once (high → deselected, medium → noted, never silently dropped). Confirmation uses `CRUDFeedback.batchImportResult(added:duplicatesSkipped:persisted:)` → "14 transactions added" / "14 transactions added · 3 duplicates skipped"; on `saveError` the drafts + thumbnails are kept so the user retries without re-picking. When the last draft leaves `drafts`, the view calls `ocrReviewStore.clear()` to release the session.

### Month detail — `MonthDetailView` + `MonthlyTransactionsService`

**The Dashboard has no transaction-status UI** — no posted/pending totals, no Pending/Posted badges anywhere (`TransactionRowView`, `MonthDetailView`, `CategoryDetailView`, `TransactionDetailView`, and the transaction editor all dropped it; it survives only in the `Transaction` model + `DuplicateMatchingService` / OCR / `SpendingAnalytics` internals). **The Dashboard shows only: the month's total spent (+ a one-line trend callout), the category donut with a collapsed-by-default row-level breakdown, the 6-month trend chart (always visible), and a collapsible "Months" list** — no separate Recurring/Non-Recurring tiles; that split is one tap away in **All Transactions** (`TransactionHistoryView`'s `RecurringFilter` segmented control) instead of living on the Dashboard itself. A month stepper in the hero + the "Months" `DisclosureGroup` (collapsed by default, `@AppStorage("dashboard.monthsExpanded")`) both open `MonthDetailView(month:)` (`@Query` filtered to `[monthStart, nextMonthStart)` in `init`). `MonthDetailView`'s summary shows total / recurring / non-recurring / count.

### `RecurringFilter`

`RecurringFilter` (`all` / `recurring` / `nonRecurring`, with `includes(_ Transaction) -> Bool`, declared at the top of `TransactionHistoryView.swift`) is the shared filter for browsing recurring vs. non-recurring transactions — `TransactionHistoryView` has a segmented `RecurringFilter` control alongside its (alphabetized) category and tag filters. Recomputes live because it's `@Query`-derived.

### Dashboard section order and the spending trend

**Dashboard, top to bottom: hero (total + trend callout) → Budget (only if a budget exists, no CTA otherwise — see Settings above) → Categories (donut, always visible, + a collapsed-by-default row breakdown) → Trend (always visible, right under Categories) → Months (collapsed).** There's no "This Month Recurring / Non-Recurring" tiles section any more — that split lives in All Transactions' `RecurringFilter` instead (see above); the Dashboard stays to "how much, on what."

`SpendingAnalytics.trailingMonths(_:endingAt:transactions:)` → `[MonthSpend { month, spent, income }]` (oldest first) backs two things: the hero's one-line **trend callout** ("Up 12% vs Aug" / "Down 8% vs Aug" / "About the same as Aug", `TrendDirection` up/down/flat with a matching arrow + tint), computed from just the last two entries of `trailingMonths(2, …)` so "how am I doing vs. last month" is visible without scrolling (`nil` — no callout — when there's no prior month or last month had nothing spent); and the "Trend" section's `SpendingTrendChart`, the last 6 months as `Charts` `BarMark`s (selected month accented) with a `LineMark` income overlay when any month has income. Unlike Months and the Categories row breakdown, the Trend chart itself is **not** collapsible — it's meant to be glanced at right after the donut.

The Categories section's row-level breakdown (`CategoryBreakdownRow` per category, each a `NavigationLink` to `CategoryDetailView`) sits inside a `DisclosureGroup("Details", isExpanded: $categoryDetailsExpanded)` (`@AppStorage("dashboard.categoryDetailsExpanded")`, collapsed by default) — the donut chart above it is never hidden. Exact-dollar-per-category and the accessibility summary are unaffected by collapse state.

### Category drill-down — `CategoryDetailView`

Each row in the Dashboard "Categories" section is a `NavigationLink` → `CategoryDetailView(categoryName:month:)`. It reads all transactions via `@Query` and filters in memory to `[monthStart, nextMonthStart)` + `(category?.name ?? "Uncategorized") == categoryName`. Header = category total (`spendingAmount` sum, excludes excluded) + month stepper + "% of month". Rows: merchant, amount, date, account, Recurring / Excluded / "Not spending" badges. `+` → `TransactionEditorView(mode: .add, initialDate: month, initialCategoryID:)`, tap → `TransactionDetailView`, swipe → Edit / Delete.

### CRUD feedback — `ToastCenter` + `.toastHost()`

One app-wide toast channel, attached once with `.toastHost()` on `RootTabView`. `ToastCenter.shared.success(_:)` / `.error(_:)` / `.show(Toast)` — a single toast at a time (a newer message replaces the current, so rapid actions never stack), auto-dismissing (errors linger longer), announced to VoiceOver via `UIAccessibility.post(.announcement)`. `CRUDFeedback` holds the consistent strings (`"Transaction added"`, `"3 transactions added"`, `"Category updated"`, `"Couldn't save transaction. Please try again."`); `CRUDFeedback.result(action:noun:count:persisted:)` is the one rule — success message only when `persisted == true`, otherwise an error `Toast`. Every CRUD site (manual add/edit, screenshot import, single + bulk delete in History/MonthDetail/Detail, category add/rename/delete-with-reassignment/hide, recurring-payment save, merchant-rule add/update/delete) calls it **inside the `do` after `try modelContext.save()`**, never before; validation errors stay as inline form messages, not toasts. `ToastCenter.init` takes an injectable `sleep` for tests.

### Visual style — `Theme` (`Views/Components/Theme.swift`)

`MyCost/Assets.xcassets` holds `AppIcon` (a generated 1024 indigo bar-chart mark, RGB / no alpha) and `AccentColor` (the same indigo, light/dark) — wired via `ASSETCATALOG_COMPILER_APPICON_NAME` / `_GLOBAL_ACCENT_COLOR_NAME` (the catalog is in the app target's Resources phase). `Theme.accent` is a code literal matching the `AccentColor` asset and is also applied via `.tint()` on `RootTabView`; decorative fills use `Theme.accent` / `.positive` / `.warning`, not `Color.accentColor`. Helpers: `Color(hex:)` (failable, 6/8-digit — the one definition, used for `Category.colorHex`), `Color(light:dark:)`, `IconBadge` (SF Symbol in a tinted rounded square), `MetricTile` (badge + title/caption + trailing value — replaced the old per-screen `MetricRow`/`RecurringMetricRow`), `.themedListBackground()` (`scrollContentBackground(.hidden)` + a soft accent wash — on every tab root), `.cardSurface()` (rounded card for a custom row; pair with `.listRowBackground(.clear)`). The Dashboard and `CategoryDetailView` totals are `cardSurface` heroes; Dashboard category rows + the donut are tinted by the real `Category.colorHex`; `TransactionRowView` / `CategoryRow` / `InlineRuleRow` use a tinted `IconBadge` and green refunds; `.themedListBackground()` is on every tab root **and** the editor `Form`s / Review / Import / detail screens. **None of this animates the app or restructures a `List`** — it's row content, row-background, and list-background modifiers only, so the SwiftUI-diff crash guards still hold.

### Logging — `AppLog` + `ModelContext.saveOrLog`

`AppLog` (`Services/AppLog.swift`) exposes category-scoped `os.Logger`s (`.data` / `.ocr` / `.rules`) over the bundle id — use one instead of `print`. `ModelContext.saveOrLog("what")` is for **best-effort background writes** — seeding, one-time migrations, `learnRule`, the rule backfill — where there's no UI to surface an error: it no-ops when `!hasChanges`, saves, and on failure logs (`.public`) rather than throwing. User-facing CRUD keeps its own `do/catch` + toast.

### Safe indexing

`.onDelete` / `.onMove` `IndexSet`s can be stale (async `@Query` update, rapid double-swipe) and caused `ContiguousArrayBuffer.swift:692: Index out of range` crashes. `Array+SafeIndexing.swift` adds `Collection[safe:] -> Element?` and `Array.elements(at: IndexSet) -> [Element]` (drops out-of-range offsets); `TransactionHistoryView` and `MerchantRulesView` delete handlers use `elements(at:)`, `CategoryManagementView.move` bounds-checks the offsets. Everywhere else the app looks items up by stable `id`, never a remembered index.

### Duplicate detection — `DuplicateMatchingService` (in `DuplicateDetector.swift`)

Operates on `DuplicateTransactionSnapshot` value types (not `Transaction`) so it stays DB-free and testable. Rules: same account required; amount must match exactly; then merchant similarity ≥ 0.78, same-day, and a pending→posted window (≤ 4 days). Similarity is `max(fuzzy token overlap, whole-string Levenshtein)` on normalized text — the token overlap counts a token as shared when it's a **≥2-char prefix abbreviation** of one on the other side ("SQ" ↔ "Square"), which processor prefixes and truncated bank descriptors produce constantly. Confidence is `none` / `medium` / `high`. `markDuplicates` writes `duplicateState` back onto `Transaction` models.

### Merchant normalization & rules — `MerchantRuleService.swift`

`MerchantRuleNormalizer.normalizedMerchantKey(for:)` strips processor prefixes (`SQ*`, `PAYPAL*`, `AMZN MKTP`…), store/ref/auth numbers, `#` codes, and trailing `STATE ZIP`, yielding an uppercase key. `caseFolded(_:)` is the lighter form (lowercase, whitespace-collapsed, trimmed) all match-type comparisons run in.

**`MerchantRule` has a `matchType`** ∈ `exact` / `startsWith` / `endsWith` / `contains` (defaulted `.exact` — lightweight migration) plus a `priority: Int` (defaulted 0). `normalizedMerchantName` / `isActive` are aliases over the stored `displayName` / `isEnabled`. `MerchantRuleService.matches(_:merchantName:originalDescription:)` tests the `caseFolded` `matchText` against **both** the merchant name and the bank's original description with the chosen operator; `.exact` additionally keeps the legacy normalized-key-equality and ≥2-token-subset fallback so pre-`matchType` rules still resolve.

**Conflict order in `bestRule`**: `priority` (higher wins outright) → match specificity (`exact` 3 > `startsWith`/`endsWith` 2 > `contains` 1) → longer `matchText` → most recently updated. So a broad `contains` never beats a more specific user rule unless the user raised its `priority`. Substring types require ≥3 chars (`matchType.minimumMatchTextLength`); the rule editor enforces it.

**Optional recurring on a rule.** `MerchantRule` also has `isRecurring` (default false) + `recurringFrequency`. `applyRules(to:rules:)` and `applyRuleToExistingTransactions` set `transaction.isRecurring = true` when a matched rule is recurring — a non-recurring rule **never** clears an existing recurring flag. Not every rule is recurring; it's opt-in per rule.

**`MerchantRuleEditorView`** is the one reusable rule sheet (match type / match text / normalized merchant name / category / recurring + frequency / active / priority / live "This rule matches: …" preview). It's presented from `MerchantRulesView` (the tab: list + swipe enable-disable / delete) and inline from `ReviewTransactionsView`'s "Edit Rule". `onSaved(rule)` hands the persisted rule back so callers can re-apply it; `onDeleted` adds a Delete button. `learnRule(…, matchType:isRecurring:recurringFrequency:)` create-or-updates by `(caseFolded matchText, matchType)` — no duplicates. The transaction editor's "Remember merchant change?" offers **"Apply to transactions containing '<name>'"** (`.contains`) or **"Apply to this exact merchant"** (`.exact`); a separate "mark future … recurring" toggle makes a recurring `.contains` rule. OCR-import merchant/category learning stays `.exact`.

**Rules apply to recent history, not just future imports — `MerchantRuleBackfillService`.** Every save from `MerchantRuleEditorView`, and every recurring `.contains` rule the transaction editor learns, runs `MerchantRuleBackfillService.apply(rules:to:recurringPayments:referenceDate:months:modelContext:)`: re-applies the whole enabled rule set (`MerchantRuleService.applyRules`) to transactions dated within the last `months` (default 3, exact date arithmetic from `referenceDate`), and links any transaction a recurring rule just flipped to a matching **active** `RecurringPayment` series (account + normalized-merchant key) so it reads as a covered occurrence on that month's Recurring page. The `@Query` rule list lags a just-inserted rule, so both call sites re-`fetch(FetchDescriptor<MerchantRule>())` first. `Outcome` (`scannedCount` / `updatedCount` / `markedRecurringCount` / `linkedToSeriesCount`, `didChangeAnything`) drives the "Applied to N recent transactions · M marked recurring" toast, which replaces the plain "Rule added/updated" toast when something changed. Backfill saves the context only when it changed something.

**Attaching an existing rule by hand — inline in `TransactionEditorView` + `MerchantRuleService.attach` / `.rulesMatching`.** The editor's "Attach a Merchant Rule" section lists the saved rules **inline** (no sheet): rules whose match text is found in the merchant name or `originalDescription` (`rulesMatching(merchantName:originalDescription:in:)`) show first as tappable `InlineRuleRow`s; everything else — disabled rules, ones whose text no longer matches after a rename — sits in a collapsed "Other rules (N)" `DisclosureGroup`, still tappable. Tapping a row calls `attachRule`: in **edit** mode it applies and **saves immediately** (`attach(rule:to:requireMatch:false)` → name / category / `isRecurring`, then `updateRecurringPayment`) so the user never hunts for Save; in **add** mode it only pre-fills the form. `applyRuleToExistingTransactions` delegates to `attach`.

**Editor progressive disclosure.** `TransactionEditorView` had accumulated Tags, Split, and Attach-a-Merchant-Rule sections on top of the core fields — all visible at once regardless of whether a given transaction needs them. The Tags and Attach-a-Merchant-Rule section *contents* are now each wrapped in their own `DisclosureGroup` (`isTagsExpanded` / `isAttachRuleExpanded`), collapsed by default and showing a one-line summary in the label (selected tag names, or "N matching rule(s) found" / "Browse N saved rules" / "No saved rules yet") — `loadInitialValues` auto-expands a group only when editing a transaction that already has something there (existing tags, or a merchant-text match). Split doesn't need its own wrapper — its "Split into categories" toggle already *is* the disclosure mechanism.

### Analytics — `SpendingAnalytics.monthlySummary`

Pure function over `[Transaction]`. Includes current-month, non-excluded rows where **`contributesToSpending`** and sums each row's **`spendingAmount`**.

**Every transaction counts by default.** `contributesToSpending == countsAsSpending`, and `countsAsSpending` is `false` **only** because the user turned it off with the editor's "Counts as spending" toggle (which also sets `spendingCountOverridden`). There is no auto-exclusion and no recurring "rescue" any more.

`spendingAmount`: `0` when the user un-counted the row; otherwise a normalized row (`.debit` / `.credit` direction, set by `TransactionNormalizer` at import / edit) returns `normalizedAmount` (positive purchase, negative refund), and a row that never went through the normalizer (`.unknown` direction — fixtures, legacy data) returns `amount` as-is. `MonthlySpendingSummary` still carries `postedTotal` / `pendingTotal` / `expectedMonthlyRecurringTotal` / `highestCategory` / `lowestCategory`, unused by any screen.

**`TransactionNormalizer`** now only does the sign flip and soft hints: a refund keyword → `normalizedAmount = -magnitude`; everything else → `+magnitude`, `countsAsSpending: true` always. `needsReview` is `true` for a sign that doesn't match the account convention (negative on a credit card, positive on chequing) so the editor can nudge the user. `isLikelyIncome` is `true` for money *in* that reads like a deposit/payroll (positive on chequing / an income keyword, not a refund) — import pre-sets `Transaction.isIncome` from it.

**Income vs. spending.** `Transaction.isIncome` (defaulted → lightweight migration; editor's "Income (money in)" toggle) marks a deposit / paycheck. An income row: `contributesToSpending == false`, `spendingAmount == 0`, and its magnitude feeds `MonthlySpendingSummary.incomeTotal` (with `netTotal = incomeTotal - total`) — the Dashboard hero shows *earned* and *net* below the spent figure when there's income. `TransactionRowView` (the row `TransactionHistoryView` uses) badges it "· Income" (not "Not counted").

`SeedDataService.countAllTransactionsByDefaultIfNeeded` (`mycost.migration.countAllByDefault.v1`) re-normalizes every existing transaction and forces `countsAsSpending = true` / `spendingCountOverridden = false`; `tagLikelyIncomeIfNeeded` (`…incomeSplit.v1`) sets `isIncome` on existing rows the normalizer reads as clear income. Both run once on launch, `UserDefaults`-gated.

`spendingCountOverridden` is set **only** when the user flips the "Counts as spending" toggle (its `Binding.set` fires — programmatic seeding in `loadInitialValues` doesn't). `TransactionRowView` and `CategoryDetailView` both tag a `!countsAsSpending` row **"Not counted"** — the same wording everywhere this state shows, matching the editor's toggle label ("Counts as spending" off → "Not counted"); it now means *the user removed it*.

**`CategorySpend` carries `percentageOfTotal`** = `amount / summary.total × 100` (the denominator is the same eligible monthly spending; `0` when the month has none; a net-refund category can be negative). `categoryTotals` stays sorted by `amount` **descending — the Dashboard's analytical order is deliberately not alphabetical**. Because every screen recomputes the summary from a `@Query` array each `body`, percentages **and** the recurring split update immediately on add / delete / amount / category / exclude / direction / refund / mark-recurring / month-move changes. `DashboardView`'s Categories section shows a native `Charts` donut (`SpendingDistributionChart` — `SectorMark`, positive categories only) plus a `CategoryBreakdownRow` per category — name, `Formatters.currencyString`, and `Formatters.percentString` all as text (VoiceOver-combined) — each a `NavigationLink` to `CategoryDetailView`, which also shows the category's "% of month" in its header.

**`recurringTotal`** = sum of `spendingAmount` over `includedTransactions.filter(\.isRecurring)`. Recurring is a plain user-controlled `Transaction.isRecurring` flag, **independent of category** — rent, mortgage, insurance, utilities, a gym membership are recurring whatever category they're in. It's editable in the Review row, the transaction editor's Tracking section, and inline on `TransactionDetailView`; import copies it from the draft; a recurring `MerchantRule` sets it automatically.

### Split transactions — `TransactionSplit`

`TransactionSplit` (`@Model`; `amount: Decimal` positive magnitude, `note`, `category: Category?`) divides one transaction's spend across categories — e.g. a $120 Costco charge as $80 Groceries + $40 Household. Owned by its `Transaction` (`Transaction.splits`, `.cascade` — deleting the transaction deletes its splits); `category` is a plain to-one (`.nullify` default, like `Transaction.category`) so deleting a category never deletes a split, just clears/reassigns it — `CategoryService.deleteCategory`/`referenceCounts` walk `transactions.flatMap(\.splits)` alongside the other reference kinds. `Transaction.isSplit`/`splitTotal` are computed.

**Analytics attribution.** `SpendingAnalytics.monthlySummary`'s `categoryTotals` attribute a split transaction's spend to each split's category instead of the transaction's own `category` (a non-split transaction is unchanged — one line at its `spendingAmount`); `total`/`recurringTotal`/`postedTotal`/etc. stay whole-transaction sums, unaffected, since the editor enforces splits summing to the transaction's amount. `SpendingAnalytics.categoryLineItems(categoryName:inMonthContaining:transactions:)` is the shared pure helper (`CategoryLineItem { id, transaction, amount, isPartial }`, includes excluded rows like the old row list did) that both feed `categoryTotals`-style grouping and power `CategoryDetailView`'s list — a split transaction contributes just its matching split's portion (badged "Split"), not its full amount, so the drill-down list and its total always agree with the Dashboard donut/percentage for that category.

**Editing.** The transaction editor's "Split" section is **edit mode only** (a transaction is split after it exists, not while first entering it) — a "Split into categories" toggle reveals rows (category picker + amount) the user adds/removes, with a live "Remaining / Over by" indicator; Save is blocked (`validateSplits`) unless every row has a positive amount and they sum exactly to the amount typed. `applySplits` reconciles `transaction.splits` by row id (update-in-place, delete-removed, insert-new) — called only from the true edit-save path, never from the add-mode duplicate-merge path (which could otherwise wipe a real target transaction's existing splits). `TransactionDetailView` shows a "Split" section listing each split's category + amount when `isSplit`. Backup/restore carry splits embedded per-transaction (`TransactionDTO.splits: [TransactionSplitDTO]?`, Optional like `tagIDs` so old backups still decode); CSV export is unchanged (still one row per transaction at its whole amount).

### Account type awareness & amount normalization — `Account` + `TransactionNormalizer`

`Account` (`@Model`, unique `name`, `accountType` ∈ `creditCard` / `debit` / `other`) remembers a source account's type so the user picks it **once**. `AccountService` does trimmed/case-insensitive name matching plus `resolveType(for:in:)` (→ `.other` if unknown), `upsert(name:type:…)`, and the static `guessAccountType(fromAmounts:) -> AccountTypeSuggestion` (≥75% of non-zero amounts positive → `.creditCard`, ≥75% negative → `.debit`, else `.other`; `isConfident` needs ≥3 samples). The **Accounts** tab (`AccountsView`) lists/edits accounts.

**Import asks the account type up front.** After OCR, `ImportView` — if the batch's account name(s) aren't a known `Account` (`knownDefaultAccountType()`) — shows a `Phase.accountType` step: a one-line guess headline (`AccountService.guessAccountType` over the candidate amounts) + a segmented `AccountType` picker pre-selected to the guess + "Looks Right — Continue". Confirming sets `OCRTransactionReviewStore.pendingDefaultAccountType` (a `@Published` on the session, reset in `clear()`); `ReviewTransactionsView.seedAccountTypes` seeds that for any account it hasn't seen before (a known `Account`'s remembered type still wins), so amounts land in Review already normalized with no sign-ambiguity `needsDirectionReview` flags. A known account skips the step (its type is set as `pendingDefaultAccountType` directly). The per-account picker in Review stays as the override / multi-account path. 0 detected still routes to `Phase.done`.

`TransactionNormalizer.normalize(originalAmount:accountType:description:)` → `NormalizedTransaction(normalizedAmount, direction, countsAsSpending, needsReview)`:
- **creditCard**: `+amount` → spending (`normalizedAmount = +amount`); `-amount` with a payment cue → not spending (`0`); `-amount` with a refund cue → reduces spending (`-amount`); `-amount` with no cue → not spending + `needsReview`.
- **debit**: `-amount` → spending (`normalizedAmount = +|amount|`); `+amount` with an income cue → not spending (`0`); `+amount` with a refund cue → `-|amount|`; `+amount` no cue → not spending + `needsReview`.
- **other**: cue-driven; `-amount` → spending; unexplained `+amount` → spending + `needsReview`.
It never blindly flips a sign that already matches the account convention. Cues are keyword lists (payment / refund / income). `Transaction` stores `amount` (bank original, sign preserved — also aliased `originalAmount`), `normalizedAmount`, `transactionDirection`, `accountType`, `countsAsSpending`, `needsDirectionReview`, plus `spendingAmount`/`applyNormalization(_:accountType:)` helpers. Applied at import (`OCRTransactionImportService`, per-account type from the Review screen) and in `TransactionEditorView` (Account Type picker + "Counts as spending" override that wins over the normalizer verdict).

### Categorization chain — `MerchantCategorizationCoordinator`

Synchronous, offline, three outcomes in strict priority: **1.** user `MerchantRule` → `.ruleMatch`. **2.** `LocalMerchantCategorizer` (offline keyword table; only applies if the mapped category name exists) → `.localMatch`. **3.** `.unresolved` → caller leaves it Uncategorized for manual categorization. No network, no AI. `ReviewTransactionsView`'s per-row "Suggest category" and `TransactionEditorView` use it; nothing is applied without the match being a concrete rule/local hit.

### Export & backup — `DataPortabilityService`

All local, no network. `transactionsCSV(_:)` → an RFC-4180 CSV (date / merchant / description / account / category / amount / type / recurring / excluded / tags / note). `makeBackup(…)` → a `Backup` Codable snapshot of every model as flat DTOs (enums as raw strings, relationships as ids); `encode` / `decode` are ISO-8601 JSON. `restore(_:into:)` **replaces everything** — `modelContext.delete(model:)` per type, then re-inserts and re-links `Transaction.category` / `.recurringPayment` / `.tags` / `.splits` and rule / series / budget categories by id. **Any field added after the initial shape must be `Optional`, not `= defaultValue`-only** — Swift's synthesized `Decodable` only fills a *missing key* automatically for an `Optional` property; a plain default is never consulted, so a non-optional field would throw `keyNotFound` decoding an older backup instead of defaulting (`Backup.tags`, `TransactionDTO.tagIDs`/`.splits` are all `Optional` for exactly this reason — see `testPreTagBackupJSONStillDecodes` / `testPreSplitBackupJSONStillDecodes`). Surfaced at **More → Settings → Backup** (`DataPortabilityView`): two `ShareLink`-style exports via a temp file + `UIActivityViewController`, a `.fileImporter` restore behind a "replace everything" confirmation, and a separate **CSV import** (below).

**CSV import.** `DataPortabilityService.parseTransactionsCSV(_:)` parses text shaped like the export — `parseCSVRows` is a small hand-written RFC-4180 tokenizer (quoted fields, doubled-quote escaping, CRLF/LF) since Foundation has no CSV parser; header names are matched case-insensitively and in any order, and only Date/Merchant/Amount are required (`CSVImportError.missingRequiredColumns` otherwise) so a trimmed-down spreadsheet still works — a row with an unparseable date/amount or empty merchant is silently skipped. `importCSVRows(...)` then resolves each row's account/category/tag **by name, creating them if they don't exist** (a re-imported export or a CSV from another app shouldn't lose that information), skips a row that's a high-confidence duplicate of an existing transaction *or* an earlier row in the same file (`DuplicateMatchingService`, snapshots accumulate as it goes), and normalizes the amount via the resolved account's type before a single save. Unlike Restore, this is **additive** — no confirmation-to-replace, just a preview count ("Found N transactions… duplicates will be skipped").

### Budgets — `Budget` + `BudgetService`

`Budget` (`@Model`; `categoryName: String?` — `nil` = overall month, else a category name matched the same way `SpendingAnalytics` groups; `monthlyLimit`). `BudgetService.progress(for:in:)` turns budgets + a `MonthlySpendingSummary` into `[BudgetProgress]` (`limit` / `spent` / `remaining` / `isOver` / `fraction`), overall first then by spend. `upsert(categoryName:monthlyLimit:…)` is one-per-scope; `renameCategory(from:to:in:)` keeps a category budget attached across a rename (wired into `CategoryService.updateCategory`). Managed under **More → Settings → Budgets** (`BudgetsView` — month navigator + progress rows + add/edit/delete); the Dashboard shows a "Budget" section with the top 4 progress rows **only when at least one budget exists** — no "set one" call-to-action there, that's Settings' job.

### Categories — `CategoryService` + `CategoryManagementView`

Categories are dynamic SwiftData records, not a fixed list. `Category` has `isActive` (hidden categories stay on existing transactions but drop out of pickers) and `isFallback` (the single protected "Uncategorized"). `Category.defaults` seeds 8 including the fallback; `SeedDataService` also calls `CategoryService.ensureFallbackCategory` on every launch so a fallback always exists.

All mutations go through `CategoryService` (stateless, `@MainActor` for the write methods): name uniqueness is enforced case-insensitively after trimming; `deleteCategory(…)` moves every reference to a chosen category or nil (→ Uncategorized) — never a silent drop — and refuses to delete/hide the fallback. `referenceCounts(for:…)` powers the "N transactions · M rules · K recurring" shown before a destructive delete.

**Merchant Rules list** (`MerchantRulesView`) is ordered **alphabetically** by `normalizedMerchantName` via `Sequence<MerchantRule>.alphabetizedByName()` (the `AttachExistingRuleView` lists too) — `priority` still decides which rule wins a conflict, it just no longer drives list order. Both `MerchantRulesView` (search `normalizedMerchantName` / `matchText` / category name) and `TransactionHistoryView` (search merchant / original description / note / account / category name / amount string) have a `.searchable` field; empty results show `ContentUnavailableView.search(text:)`. Delete offsets in `MerchantRulesView` resolve against the filtered `displayedRules`. **`TransactionHistoryView` defaults to the current month** (`scopeIsMonth` + `monthAnchor`, `MonthlyTransactionsService.transactions(inMonthContaining:)`): a month-navigator row steps months (capped at the current month), and an "All" toggle switches to all-time (toggling back to "By month" resets to the current month). Category / recurring / search filters apply within the active scope.

**Category ordering.** `Sequence<Category>.alphabetizedByName()` (`localizedCaseInsensitiveCompare`) is the order for everywhere the user **selects or manages** categories — the `CategoryManagementView` list (no manual reordering anymore) and the pickers in the transaction editor, merchant-rule editor, recurring-payment editor, deletion-reassignment, and OCR Review. It is **never** applied to the Dashboard, which keeps its spending-ranked `categoryTotals`. `Category.sortOrder` still exists on the model (and `CategoryService.reorder`) but no longer drives any list.

### Tags — `Tag` + `TagService`

`Tag` (`@Model`, unique `name`, optional `colorHex`) is a free-form label **orthogonal to `Category`** — a transaction has one category but any number of tags. Many-to-many: `Transaction.tags` (`.nullify`, defaulted → lightweight migration) with `Tag.transactions` as the inverse; deleting a tag only detaches it. All mutations go through `TagService` (stateless, `@MainActor` writes, mirrors `CategoryService`/`AccountService`): `normalizedName` (trim + lowercase), `tag(named:in:)`, `isNameAvailable`, `upsert(name:in:modelContext:)` (create-or-reuse by case-insensitive name), `rename`, `delete` (detaches from every transaction then removes the tag — transactions untouched), `attach`/`detach`, and `setTags(_:on:allTags:)` (reconcile a transaction's tags to an exact id set). `Sequence<Tag>.alphabetizedByName()` orders every tag list/picker.

**UI.** The transaction editor has a collapsed-by-default "Tags" `DisclosureGroup` — check-toggle rows for existing tags plus a "New tag" field (`addTypedTag` → `TagService.upsert`, then select by the returned id since `@Query` lags); `applyTags(to:)` reconciles on Save (both add and edit paths, and the merge path) via a fresh `FetchDescriptor<Tag>()` merged with `allTags`. **Tags don't require the full editor** — `TransactionDetailView` shows the comma-joined tag list (or "No tags") plus an "Edit Tags" button that presents `TransactionTagPickerView`, the same check-toggle-rows-plus-new-tag-field UI as a standalone sheet; every tap calls `TagService.attach`/`.detach`/`.upsert` and saves immediately (`modelContext.saveOrLog`, no separate Save — same philosophy as the Recurring toggle right above it), so adding or removing a tag never requires opening `TransactionEditorView`. `TransactionHistoryView` has a `TagFilter` picker (shown when any tag exists) applied after the recurring filter, and `.searchable` also matches tag names; its batch-edit "Tag" action (`BatchTagPickerView`) adds tags to every selected transaction the same way. **More → Tags** (`TagManagementView`) lists tags alphabetically with their transaction count, add / rename (alert) / swipe-delete (confirmation names the count). Backup/restore carry tags (`TagDTO` + `TransactionDTO.tagIDs`, defaulted so pre-tag backups still decode); the CSV export has a `Tags` column (`; `-joined).

### Recurring — `Transaction.isRecurring` (user-controlled) + `RecurringPaymentSuggestionService`

The source of truth for "this month's recurring spend" is the per-transaction `isRecurring` flag; `SpendingAnalytics.recurringTotal` / `nonRecurringTotal` split on it. It's editable in the Review row, the transaction editor's Tracking section, and inline on `TransactionDetailView` (which toasts "Recurring status updated"). The dedicated view is `TransactionHistoryView`'s `RecurringFilter` segmented control. `RecurringPaymentSuggestionService` still auto-*suggests* series (account + normalized merchant key ≥ 2, infers frequency, rejects irregular cadence / high variance), but marking recurring never requires a suggestion or a "Subscription" category.

**Every plain on/off field on a transaction is inline-editable on `TransactionDetailView`, not just Recurring** — Income, Counts as spending (hidden when Income is on, matching the editor), and Exclude from totals (+ its Reason `TextField`, shown only while excluded) are each a `Toggle` bound directly to the transaction with a `set` that saves immediately and toasts ("Income status updated" / "Spending status updated" / "Exclusion status updated"), reverting the toggle and showing an error toast on a save failure — the same pattern `setRecurring` already used. `setCountsAsSpending` sets `spendingCountOverridden = true` (freezing the choice, same as the editor's toggle) but deliberately leaves `normalizedAmount` untouched: `spendingAmount` already returns `0` whenever `!contributesToSpending` regardless of the stored amount, so a plain flip needs no renormalization. **The rule of thumb going forward: a field that's just a boolean shouldn't require opening `TransactionEditorView` to flip** — only fields needing a picker, a multi-part form (Split, the recurrence-frequency editor), or cross-field validation belong in the full editor.

**`RecurringPaymentsView` — the selected month is the single source of truth.** Everything under the month stepper is generated *strictly within* `monthAnchor`'s calendar month and regenerated on every step. `RecurringPaymentSuggestionService.monthlyExpectation(activeSeries:recurringTransactions:inMonthContaining:)` returns a `RecurringMonthExpectation`: per-series **expected occurrences** whose dates fall in that month (`expectedOccurrenceDates` → `recurringPayment.schedule().occurrences(inMonthContaining:)`), plus `expectedTotal` (Σ those occurrences × `expectedAmount`), `matchedTotal` / `completedCount` (occurrences covered by that month's actual `isRecurring` transactions — a transaction **explicitly linked** to the series via `recurringPayment` counts for it regardless of name; an unlinked one falls back to the account+normalized-merchant key; first-N greedy), `remainingTotal`, `expectedCount`, `remainingCount`. So a biweekly mortgage shows **2 or 3** occurrences depending on the month, a monthly series 1, a yearly series only in its due month (never 1/12 every month). `Occurrence.id` is value-derived (safe for `ForEach` over the recomputed array). `occurrenceCount` / `expectedAmount(for:inMonthContaining:)` are thin wrappers over `expectedOccurrenceDates`. The old annualized `expectedMonthlyAmount(for:)` is unchanged and feeds only `SpendingAnalytics.expectedMonthlyRecurringTotal` (no screen).

**Needs Attention + reminders.** A today-relative "Needs Attention" section at the top of the Recurring tab (`RecurringPaymentSuggestionService.attention(activeSeries:recurringTransactions:now:soonDays:graceDays:lookbackDays:)` → `RecurringAttention { dueSoon, missed }`): occurrences due within 7 days and unpaid, or 2+ days past and unpaid (never earlier than the series' `nextExpectedDate`), matched by link/key + first-N-greedy. **All of `attention`'s window math (`windowStart`/`windowEnd`/`missedCutoff`) and the final due/missed split work in whole calendar days off `today = calendar.startOfDay(for: now)`, never the raw `now` timestamp** — occurrence dates are midnight-anchored, so comparing them against a precise `now` (`date >= now`) made a payment due *later today* silently vanish from both lists the moment any time had passed since midnight (a biweekly due today, checked at 11am, was neither `>= now` nor old enough to be "missed" — see `testAttentionShowsAPaymentDueLaterTodayEvenWhenCheckedInTheAfternoon`). A "Reminders" section (`@AppStorage("recurring.reminderLeadDays")`, 0 = off, days-only Stepper 1…14) drives `RecurringReminderService` — local `UNCalendarNotificationTrigger`s (id `mycost.recurring.<seriesID>`, 9am, `leadDays` before each active series' next date); `sync` clears + reschedules on every change / `.task`, and asks for notification permission only when the toggle is turned on.

**One combined table.** Below that: a "This Month" summary section (month stepper + Expected / Actual / Remaining / Occurrences metric rows), then **one** "Recurring — <month>" section, then Suggestions. The combined section has one `SeriesMonthRow` per series (`seriesRows` — active first then paused, each alphabetical by merchant, carrying that month's grouped `Occurrence`s): merchant · schedule label · account, this month's amount, and a dot per expected occurrence — `checkmark.circle.fill` green when it has happened, hollow `circle` when still due — plus `completed/total`. Tap → `RecurringPaymentEditorView`; swipe → Pause/Resume or Delete, all via `RecurringPaymentService` (**transactions are never touched**). Recurring transactions in the month with no series and whose account+merchant key matches no active series are listed after under "Not linked to a series" as `UnifiedLooseTransactionRow` (always green-checked — they happened; tap → `TransactionDetailView`).

**Editing / pausing / deleting a series — `RecurringPaymentService`.** The "Recurring Payments" section rows are tappable (chevron) → `RecurringPaymentEditorView` (a sheet). Swipe **right** = Pause / Resume (`setActive` → `RecurringPayment.isActive`); swipe **left** = Delete (confirmation dialog). Both go through `RecurringPaymentService` (`@MainActor` struct, mirrors `AccountService`/`CategoryService`). **A series is only a schedule — never the owner of a transaction.** `delete(_:modelContext:)` explicitly sets `transaction.recurringPayment = nil` on each linked transaction and removes *only* the series record — every transaction stays in the store with its amount, date, category and `isRecurring` flag exactly as they were (the `.nullify` inverse on `RecurringPayment.transactions` also guarantees no cascade; the explicit unlink makes the intent testable). A paused series drops out of `expectedThisMonth` / `monthlyExpectation` (both filter `activeSeries` = `recurringPayments.filter(\.isActive)`) but its transactions and link are untouched.

**Flexible recurrence — `RecurrenceSchedule` + `RecurrenceRuleEditor`.** `RecurrenceFrequency` adds `everyNMonths`, `nthWeekday`, `nthBusinessDay` (`isAdvanced == true`) alongside the fixed periods. `RecurringPayment` carries `monthInterval` (everyNMonths gap; 6 = semi-annual), `weekdayOrdinal` (1…5 or -1 = last), `weekday` (Calendar 1=Sun…7=Sat) — all defaulted → lightweight migration. `RecurrenceSchedule` (pure value type, `Services/RecurrenceSchedule.swift`) is the one place occurrence dates + the human label are generated: fixed periods walk from the anchor; `everyNMonths` fires once in every Nth month from the anchor's month, on the anchor's day-of-month (clamped to short months); `nthWeekday` / `nthBusinessDay` compute the month's date directly (weekends skipped for business days; holidays not modelled). `RecurringPayment.schedule(calendar:)` builds one from the stored fields + `occurrenceAnchor` (latest linked txn → `nextExpectedDate` → `createdAt`). `RecurrenceRuleEditor` (`Views/Components/`) is the shared frequency picker + per-mode sub-controls, used by `RecurringPaymentEditorView` and `TransactionEditorView`'s Tracking section; both thread `monthInterval`/`weekdayOrdinal`/`weekday` through load/save and refresh `nextExpectedDate` via `schedule.nextOccurrence(after:)`. Display labels (`RecurringPaymentRow`, `TransactionDetailView`, `MonthRecurringRow`, `TransactionRowView`) use `payment.schedule().label` ("First Monday of the month", "Every 6 months", "Every 45 days").

### Navigation & the persistent review session

`RootTabView` = **3 tabs**: Dashboard, Recurring = `RecurringPaymentsView`, More = `MoreView`. Categories and Rules are not tabs — they're daily-*occasional*, not daily-*use*, so they live under **More → Organize** (`CategoryManagementView` / `MerchantRulesView`, `more.categories` / `more.rules`) alongside **Manage** (All Transactions / Budgets / Tags / Accounts / Export & Backup) and **Privacy** (App Lock). A `@StateObject AppNavigationModel` (`nav`) drives two root-level sheets via `.sheet(item: $nav.route)` — `.importPicker` (`ImportView`) and `.review` (`ReviewTransactionsView`) — plus `nav.isShowingImportConflict`.

- **Import** is a Dashboard toolbar button → `nav.requestImport(session:)`: opens `.importPicker` directly, or if `session.hasActiveSession`, shows a `confirmationDialog` — **Continue Current Review** (`nav.continueCurrentReview()` → `.review`, session untouched) / **Replace with New Import** (`nav.replaceReview(session:)` → `session.clear()` then `.importPicker`) / **Cancel**. An unfinished session is never discarded silently.
- **Review** is a persistent working session, not a modal. `OCRTransactionReviewStore` (a root `@StateObject`) holds every draft + all edits (merchant, category, include/exclude, recurring, rule attribution, duplicate decisions); closing the sheet (`Close`) doesn't touch it. While `hasActiveSession`, a **compact floating button in the bottom-trailing corner** (`reviewFloatingButton` — a 52pt `checklist` circle in `Theme.accent` with a red count badge, `accessibilityIdentifier("app.reviewBanner")`, `.transaction { $0.animation = nil }`) and a `MoreView` row re-open `.review`. **The affordance is gated only on `hasActiveSession`, never on `nav.route`** — a `List` behind an animating sheet must not reflow as the session starts/ends.
  - It's drawn as an **`.overlay(alignment: .bottomTrailing)` on the `TabView`**, `.padding(.bottom, 66)` to float clear of the ~49pt tab bar. This is the fourth shape, after three that shipped or nearly shipped broken: (1) a **top `.safeAreaInset`** collided with a pushed screen's own nav bar / `.searchable` field (rendered overlapping instead of pushed below); (2) a **bottom `.safeAreaInset` directly on the `TabView`** fought the tab bar's own bottom-safe-area handling and **hid the tab bar entirely** (a real regression — user screenshot, "I'm even unable to pick the tabs from below now"); (3) a **full-width `VStack` sibling below the `TabView`** worked but ate a horizontal strip on every screen and crowded the tab bar. An `.overlay` changes nothing about the content's layout, so toggling it can't trip `List`'s diff (`ContiguousArrayBuffer:692`), and a corner button overlaps neither the tab bar (floats above it) nor any screen's nav chrome. Verified empirically by `testReviewBannerNeverObscuresTheTabBarOrASearchField` (`MyCostUITests`) — a real OCR review session isn't XCUITest-drivable, so the launch argument `-ui-testing-seed-review` makes `RootTabView.seedReviewSessionForUITestingIfRequested()` seed `ocrReviewStore` with two synthetic candidates on launch.
- The Review list iterates **`ForEach(ocrReviewStore.drafts)` by identity** (not `ForEach($binding)`) and hands each row a `draftBinding(for: id)` that resolves the draft by `id` (falling back to `OCRTransactionDraft.placeholder`), never a stale array index — a positional binding-ForEach crashes when the array shrinks under a row teardown. When the last draft leaves `drafts` (imported, or removed one-by-one), `ReviewTransactionsView` `dismiss()`es first and defers `ocrReviewStore.clear()` (~450 ms) until the sheet is gone; a partial import removes only the imported drafts and stays open.
- After `saveApprovedTransactions` imports everything and `drafts` is empty, `ReviewTransactionsView` calls `ocrReviewStore.clear()` and `dismiss()` — banner and shortcut disappear; the next import starts a fresh session.
- Session state is memory-only (not persisted across relaunch). The only image data it retains is `sourceThumbnails` (downscaled ≤480px); full-resolution `UIImage`s are dropped the moment processing finishes.

### Startup

`RootTabView.task` calls `SeedDataService.seedDefaultCategoriesIfNeeded` on every launch; it no-ops if any `Category` exists. The 8 default categories are `Category.defaults`.

### First-run onboarding — `OnboardingView`

`RootTabView` presents `OnboardingView` in a `.fullScreenCover` gated on `@AppStorage("mycost.hasOnboarded")` (default `false`), suppressed under `-ui-testing` so UI tests launch straight into the tabs. Three paged screens (`TabView(.page)`): what MyCost does, screenshot import, and an optional "your main account" picker. Dismissing the cover (Get Started, Skip, or the setter path) flips `hasOnboarded = true`; picking Credit card / Chequing on the last page `AccountService.upsert`s a "Default" `Account` with that type so the first import can skip the guess-and-confirm step. View-only — no new service logic.

### App Lock — `AppLockService` + `AppLockView`

`AppLockService` wraps `LocalAuthentication` (`.deviceOwnerAuthentication` — biometrics *or* device passcode, so a phone without Face ID/Touch ID or with biometrics temporarily unavailable still works). `RootTabView` gates a `.fullScreenCover(AppLockView)` on `@State private var isLocked`, initialized in a custom `init()` from `@AppStorage("mycost.appLockEnabled")` *and* the grace check below, so a cold launch never flashes content before the lock screen but also doesn't re-prompt if it's still within the grace window. `AppLockView.onAppear` immediately prompts, and its "Unlock" button retries by hand. The toggle lives in **Settings** (see below), which checks `AppLockService.canAuthenticate()` before turning it on and shows an alert instead of silently enabling a lock the user could get stuck behind on a device with no passcode set.

**Grace period — `AppLockService.isWithinGrace` + `@AppStorage("mycost.appLockGraceMinutes")`.** 0 (default, "Immediately") re-locks the instant the app backgrounds, same as before; a Settings `Picker` (1 / 5 / 10 / 15 / 30 / 60 minutes) tolerates a brief background window without re-prompting — the same idea as iOS's own Face ID & Passcode "Require Passcode" setting. `RootTabView.onChange(of: scenePhase)`: on `.background`, stamps `@AppStorage("mycost.appLockLastBackgroundedAt")` (persisted, not just `@State`, so the window survives the app being suspended *or* killed and relaunched) and, only when the grace is 0, locks immediately; on `.active`, it only evaluates a relock **when `lastBackgroundedTimestamp > 0`** — skipping that (and clearing the timestamp after every real evaluation) is what stops a Control Center pull-down or similar `.inactive` blip, which never truly backgrounds the app, from causing a false mid-use relock. `isWithinGrace(graceMinutes:lastBackgroundedAt:now:)` is the one pure rule both `init()` and the scene-phase handler share — unit-tested directly (`testAppLockGraceWindowRule`) since it's `@testable`-reachable as a `static func` on the service, not a private view method. **Known trade-off, matching iOS's own equivalent setting**: with a grace period > 0, the app switcher can show the last visible screen during that window (there's no separate always-on privacy blur) — the grace period only governs whether *re-authentication* is required, not switcher-preview privacy.

### Settings — `SettingsView`

Every preference/configuration control in the app lives in **one place** — More → Settings (`settings.*` identifiers) — deliberately kept out of Dashboard and Recurring so those screens show only their own content, never a settings prompt mixed into it:
- **Budget** — a link to `BudgetsView` (setting limits is a configuration action; *viewing* progress stays on the Dashboard, see below), plus the budget-alert toggle + threshold `Stepper` (50…100%, step 5, default 90 — see Budget alerts below).
- **Recurring Reminders** — the lead-days toggle + `Stepper` (1…14, days) that used to sit on the Recurring tab; unchanged mechanics (`RecurringReminderService.sync`, requests notification permission only when turned on), just relocated. Recurring itself still keeps a `.task(id: recurringPayments.count)` background re-sync so reminders stay current even if the user never opens Settings after adding/editing a series.
- **Backup** — a link to `DataPortabilityView` whose subtitle live-shows `DataPortabilityService.isBackupOverdue`-driven status ("Last backup: …" / "Never backed up", `Theme.warning`-tinted once overdue) instead of a separate Dashboard banner.
- **Privacy** — the App Lock toggle + its grace-period `Picker` (see App Lock above).

`DashboardView` no longer has a "Set a monthly budget" call-to-action (the Budget section simply doesn't render when there are no budgets — no CTA in its place) or a "Back up your data" banner; both actions moved to Settings.

### Small polish batch — merchant autocomplete, chart VoiceOver summaries

- **Merchant autocomplete.** `TransactionEditorView`'s Merchant field has `@FocusState`; while focused and non-empty, up to 5 distinct past merchant names containing the typed text (case-insensitive, excluding an exact match) appear as tappable rows right below it (conditional rows in an always-present `Section` — safe per the List-diff rule above). Pure view-level filtering, not a service — mirrors how `TransactionHistoryView.filteredTransactions` isn't extracted either.
- **Chart VoiceOver summaries.** Swift Charts marks aren't individually accessible, so `SpendingTrendChart` and `SpendingDistributionChart` (`DashboardView`) each collapse to one `.accessibilityElement(children: .ignore)` carrying a composed `.accessibilityValue` ("Aug $200, Sep $150, …" / "Groceries 40%, Dining 25%, …") instead of being a silent stop in the swipe order. The exact-dollar detail still lives in the text rows below (`CategoryBreakdownRow`), unaffected.

### Batch edit — `TransactionHistoryView`

A "Select" toolbar button toggles `isSelecting`; while on, each row swaps its wrapper from `NavigationLink` to a `Button` that toggles membership in `selectedIDs` (a leading checkmark/circle icon, `TransactionRowView` itself unchanged) — a per-row content variation inside a stably-identified `ForEach`, not a whole-`Section` add/remove, so it doesn't trip the List-diff rule above. A bottom toolbar (`ToolbarItemGroup(placement: .bottomBar)`) offers **Category** (folder icon, `BatchCategoryPickerView` sheet — sets one category on every selected transaction), **Tag** (tag icon, `BatchTagPickerView` sheet — multi-select, *adds* the chosen tags to each selected transaction's existing set, never replaces it), and **Delete** (trash icon, confirmation dialog → `TrashBin.shared.deleteTransactions`, so a bulk delete is undoable exactly like a single one) — each a `Label` (icon + text), not text-only, for scannability. All three exit selection mode afterward.

### Undoable delete — `TrashBin`

Deleting a transaction is deferred, not immediate. `TrashBin` (`@MainActor` `ObservableObject` singleton, `.shared`, mirrors `ToastCenter`) tracks `pendingDeletionIDs: Set<UUID>`; `scheduleDeletion(ids:perform:)` adds ids to that set and returns a token, then after a grace period (default 4s, injectable for tests like `ToastCenter`'s `sleep`) runs `perform` (the real `modelContext.delete` + `saveOrLog`) unless `cancel(token)` ran first. `TrashBin.deleteTransactions(_:modelContext:)` is the one shared entry point every delete site calls — it schedules the batch and shows a `Toast` with an "Undo" action (`actionLabel`/`action` on `Toast`, rendered by `ToastView` as an inline button; an actionable toast gets the longer 5s duration so it outlives the 4s grace period, and skips `accessibilityElement(children: .combine)` so VoiceOver can reach the button instead of only a static-text summary).

Every screen with a delete affordance — `TransactionHistoryView` (swipe/bulk `.onDelete`), `TransactionDetailView` (confirmation dialog, `dismiss()`s immediately), `CategoryDetailView`, `MonthDetailView` — holds `@ObservedObject private var trashBin = TrashBin.shared` and filters its working transaction list (`!trashBin.contains($0.id)`) before computing rows *and* totals, so the row disappears and the total updates the instant Delete is tapped, not after the grace period. This is deliberately **UI-layer-only state**, not threaded into `SpendingAnalytics` or any other pure service — a *different* screen's own `@Query`-derived total (e.g. the Dashboard, which isn't in this list) can lag the grace period by a few seconds. That's accepted, not a bug: the deletion hasn't actually happened in the store yet.

### Recently Deleted — `DeletedTransactionRecord` + `RecentlyDeletedService`

The grace period is only 4 seconds — too short if you don't notice the toast. Once it elapses, `TrashBin.deleteTransactions`'s `perform` closure archives each transaction to a `DeletedTransactionRecord` (a flat snapshot — id, amount, dates, category by both id-to-relink and name-to-display, tag names — mirrors the DTO shape `DataPortabilityService` already uses for backup) **before** deleting it, so it's still recoverable from **More → Manage → Recently Deleted** for 30 days. The live `Transaction` really is gone (nothing else needed a `deletedAt` filter threaded through every `@Query` in the app), while the archive is a separate model, same as how Photos/Notes/Files actually implement a "Recently Deleted" folder.

`RecentlyDeletedService`: `isExpired`/`daysRemaining` (pure, `retentionDays = 30`); `purgeExpired(_:modelContext:)` (called from `RecentlyDeletedView.task` on every appearance); `restore(_:categories:tags:modelContext:)` re-creates a live `Transaction` with the same id, re-linking category by id (falling back to none if it's gone) and tags by name (creating one that no longer exists — same philosophy as CSV import), then deletes the record; `deletePermanently(_:modelContext:)` just forgets the record. **Restoring a transaction does not restore its splits or its recurring-series link** — a documented scope cut, not a bug: this is a safety net for "I deleted the wrong thing yesterday," not a full-fidelity undo. `RecentlyDeletedView` lists records newest-first with swipe actions (Restore / Delete Permanently, the latter behind a confirmation), a days-remaining caption per row, and a badge count on its `MoreView` row.

### Budget alerts — `BudgetAlertService`

A local notification the first time a budget's spend crosses a configurable threshold (`@AppStorage("budgets.alertsEnabled")`, `"budgets.alertThresholdPercent"` — Stepper 50…100 step 5, default 90 — both in Settings' Budget section) each calendar month. **There's no reliable background execution in this app** (no server, no push, no background refresh configured) — `DashboardView.task(id: transactions.count)` is the check point, so "as soon as it crosses" really means "the next time the app computes budget progress while foregrounded," which in practice is whenever spending could have changed (the user is always in the app for that: adding a transaction, importing screenshots, editing one). The check always uses the **real current month** (`Date()`), never `monthAnchor` — an alert about a month the user is just browsing historically would be meaningless. `checkThresholds(_:thresholdFraction:now:)` keys "already notified" by `budgetID|yyyy-MM` in `UserDefaults` (injectable, so tests never touch real device state) so a budget already over the threshold doesn't re-notify on every subsequent check, but does again next month.

### Home Screen quick actions — `AppDelegate` + `QuickAction`

Two static shortcuts (long-press the app icon): "Add Transaction" and "Import Screenshots", declared in `MyCost/Info.plist`'s `UIApplicationShortcutItems` (the only reason that file isn't the usual empty `<dict/>` — `GENERATE_INFOPLIST_FILE` merges its own keys with the `INFOPLIST_KEY_*` build settings, and a shortcut-items *array* can't be expressed as a scalar `INFOPLIST_KEY_*`). SwiftUI has no native hook for shortcut activation, so a small `AppDelegate` (`@UIApplicationDelegateAdaptor` in `MyCostApp`) captures *which* one was tapped into `AppDelegate.pendingShortcutType` (both `didFinishLaunchingWithOptions` for a cold launch via shortcut, and `performActionFor` for a warm one) — a static hand-off point, since the delegate exists before any SwiftUI view does. `RootTabView` consumes it in `handlePendingShortcutIfUnlocked()`, called from **both** `.onChange(of: scenePhase)` going `.active` **and** `.onChange(of: isLocked)` going `false` — a shortcut tapped while App Lock is showing stays pending (never jumps straight to "Add Transaction" past the lock screen) and fires the moment the app unlocks instead of being lost.
